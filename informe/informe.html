Parte A

Trabajo colaborativo en GitHub

Creamos un repositorio privado y protegimos main para exigir Pull Requests, resolución de comentarios y una aprobación. Cada cambio se desarrolló en una rama feature/..., fue revisado por otro integrante y se integró después de atender sus observaciones.

Issue→Rama→Commit→PR→Revisión→Merge

Los commits pequeños y descriptivos permitieron identificar quién realizó cada aporte. Los Issues vincularon cada tarea con su PR y se cerraron automáticamente al fusionar los cambios.

2

Parte A

Conflicto y revisión de código

El conflicto ocurrió porque dos ramas creadas desde la misma versión de main modificaron el mismo título de index.html. Después de fusionar la primera rama, Git no pudo elegir automáticamente cuál texto conservar en la segunda.

Cómo lo resolvimos

  1. Actualizamos la rama pendiente con los cambios recientes de main.
  2. Revisamos los marcadores <<<<<<<, ======= y >>>>>>>.
  3. Acordamos el título definitivo y eliminamos los marcadores.
  4. Confirmamos la solución con un nuevo commit y actualizamos el PR.

Este proceso mostró que Git detecta la incompatibilidad, pero el equipo debe decidir el contenido correcto. El comentario de revisión dejó evidencia de la decisión y de la participación cruzada.

Partes B, C y D

Red privada y servidor propio

Tailscale

Conectó las cuatro laptops mediante una red privada cifrada. Así accedimos al anfitrión por su IP 100.x.x.x sin abrir puertos en el router.

Gitea

Alojamos un segundo remoto Git. El primer push transfirió también la historia creada durante la etapa de GitHub.

Cuando cerramos la terminal de Gitea, el servidor dejó de responder. Los commits locales continuaron funcionando porque cada clon conserva la historia completa. Usamos la IP de Tailscale porque localhost siempre apunta al equipo desde el cual se escribe, no a la laptop del anfitrión.

Dos remotos, el mismo Git

4

Comprensión

Preguntas 1–3

1. ¿Qué diferencia hay entre Git, GitHub y Gitea?

Git registra versiones en cada computadora y funciona sin conexión. GitHub y Gitea alojan repositorios para compartirlos y añaden Issues y Pull Requests. GitHub es un servicio administrado en la nube; Gitea se instala en infraestructura propia y deja su mantenimiento en manos del equipo.

2. ¿Para qué sirve una rama?

Una rama permite desarrollar un cambio sin alterar de inmediato la versión estable. En la práctica cada perfil tuvo su propia rama, lo que permitió revisar y corregir el trabajo antes de integrarlo. La protección de main evitó publicar cambios directos sin revisión.

3. ¿Qué es un conflicto y cómo se resolvió?

Es una incompatibilidad que Git no puede resolver automáticamente. Ocurrió al cambiar la misma línea desde dos ramas. Actualizamos la segunda rama, elegimos el título acordado, eliminamos los marcadores y guardamos la solución en un commit.

Cada integrante debe revisar y adaptar con sus propias palabras al menos una respuesta antes de entregar.

5

Comprensión y reflexión

Preguntas 4–6

4. ¿Qué problema resolvió Tailscale?

Permitió comunicar laptops ubicadas en redes distintas como si compartieran una red local privada. Sin Tailscale, desde casas diferentes no alcanzaríamos la IP local del anfitrión y tendríamos que publicar un puerto o usar infraestructura externa.

5. ¿Por qué funcionaron los commits con Gitea apagado?

Git es distribuido: cada clon contiene el proyecto y su historia. Gitea solo hizo falta para compartir cambios mediante push y pull. Al encenderlo de nuevo, enviamos los commits acumulados.

6. ¿Cuándo conviene usar Gitea?

Conviene cuando una organización debe mantener el código en su propia red o aplicar controles internos. Una institución pública podría alojar allí un sistema con integraciones sensibles, asumiendo las actualizaciones, seguridad y copias de respaldo.

Reflexión final

El servidor en la laptop ofreció control, privacidad y bajo costo, pero dependió de su energía, conexión y disco. GitHub aportó mayor disponibilidad y mantenimiento administrado. Para un entorno real ejecutaríamos Gitea en un equipo dedicado y programaríamos respaldos.
